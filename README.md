# ScamShield AI

**Advisory scam-content investigation workstation**

ScamShield AI preserves suspicious emails, SMS messages, and online advertisements, records forensic metadata, and produces an advisory reading of possible scam and phishing indicators. The reading does not prove that content is fraudulent and does not decide whether the text was written by a person or generated by AI.

## Project objectives

- Analyze submitted email, SMS, and advertisement text for potential scam and phishing indicators.
- Preserve submitted text as investigation evidence.
- Record a SHA-256 hash and UTC evidence collection timestamp.
- Store investigation records in SQLite and support later integrity verification.
- Generate downloadable PDF forensic reports.
- Use an existing AI model through an API; this project does not train a machine-learning model.

## Technology stack

- Python
- FastAPI backend
- Streamlit workstation
- OpenAI Python SDK Responses API for backend advisory analysis
- SQLite for investigation records
- Python `hashlib` for SHA-256 hashing
- ReportLab for PDF reports, with bundled DejaVu fonts
- Pydantic for data validation
- python-dotenv for environment configuration
- pytest for testing

## Current status

The workstation is usable end to end.

- `mock` and `openai` analysis providers.
- Evidence is preserved with its SHA-256 baseline and UTC collection time before analysis runs.
- Failed analysis keeps the evidence, records `ANALYSIS_FAILED`, and can be run again.
- A completed advisory result is kept unless a replacement is explicitly requested. The prior summary is recorded as an event.
- Integrity verification and the forensic event history are available.
- PDF reports are generated on request, stored under `reports/`, and hashed. The digest is stored in the database and is not embedded in the file.
- The Streamlit workstation submits evidence, reviews cases, verifies integrity, and downloads reports.
- Optional `SCAMSHIELD_API_KEY` protects `/api/v1` routes. `/health` and `/health/ready` stay open for process checks.

Step-by-step commands, the first-run check, and troubleshooting are in [HOW_TO_RUN.md](HOW_TO_RUN.md).

## Windows setup and run

Run these commands in PowerShell from the project root:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
```

Start the API and the workstation in two terminals:

```powershell
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
python -m streamlit run frontend/app.py --server.address 127.0.0.1 --server.port 8501
```

Or start both with:

```powershell
.\scripts\start.ps1
```

- Workstation: `http://127.0.0.1:8501`
- API docs: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`

Run the tests from the project root:

```powershell
python -m pytest
```

The `.env` file is for local configuration and is excluded from version control. For offline use, keep `AI_PROVIDER=mock`. No key or model is required. Mock results are labeled and inconclusive; they do not analyze the submitted content.

To use the OpenAI API, set `AI_PROVIDER=openai`, set `OPENAI_API_KEY` to your own key, and set `OPENAI_MODEL` to a model available to your account that supports the Responses API structured output. The project does not choose a model for you. Only the backend calls the model. Never commit API keys.

Optional settings:

- `DATABASE_PATH` and `REPORTS_DIR` override the default SQLite file and report directory.
- `SCAMSHIELD_API_KEY`, when set, requires every `/api/v1` request to send the same value in `X-API-Key`. Put the same value in the workstation sidebar, or in `SCAMSHIELD_API_KEY` for the Streamlit process.
- `SCAMSHIELD_API_URL` tells the workstation where the API is. The default is `http://127.0.0.1:8000`.
- `LOG_LEVEL` controls backend logs. Logs record case and report identifiers, not evidence text or secrets.
- `CORS_ORIGINS` is a comma-separated list of browser origins. Leave it blank when only the Streamlit workstation is used.

## Docker

From the project root, with Docker Compose:

```powershell
docker compose up --build
```

The API listens on port `8000` and the workstation on port `8501`. The database and PDF files persist in the `scamshield-data` volume. Set `OPENAI_API_KEY`, `OPENAI_MODEL`, and `AI_PROVIDER` in the shell or in a `.env` file beside `docker-compose.yml` before starting live analysis. Compose reads those names for substitution.

## API

Create and analyze an investigation:

```http
POST /api/v1/analyze
Content-Type: application/json
```

```json
{
  "evidence_type": "EMAIL",
  "content": "Suspicious message text goes here."
}
```

`evidence_type` is `EMAIL`, `SMS`, or `ADVERTISEMENT`. `content` must contain non-whitespace text and be at most 20,000 characters.

The `201 Created` response includes the case ID, forensic metadata, `analysis_status`, `analysis_provider`, and structured analysis fields. In OpenAI mode, each indicator includes an exact `evidence_quote` from the submitted text and an explanation, plus recommended actions and limitations. The service does not visit URLs or provide confidence scores.

If analysis fails, the evidence is still retained, its status becomes `ANALYSIS_FAILED`, and an event is recorded. The request returns `429` for rate limits, `502` for provider or malformed-response errors, `503` for configuration errors, or `504` for timeouts. The error body includes the preserved `case_id`.

Run analysis again for a failed or pending case:

```http
POST /api/v1/cases/{case_id}/analyze
Content-Type: application/json

{}
```

A completed case returns `409 Conflict` unless the body is `{"replace_completed": true}`. Replacement records the previous provider, risk level, and summary, then stores the new advisory result. The original evidence and its digest are not changed. The workstation explains this with the "Replace a completed analysis" control.

Other case routes:

- `GET /api/v1/cases` lists cases, newest first. Optional `limit` (1–500) and `offset` page the list.
- `GET /api/v1/cases/{case_id}` returns one case, including the stored text.
- `POST /api/v1/cases/{case_id}/verify-integrity` compares the stored text with its SHA-256 baseline.
- `GET /api/v1/cases/{case_id}/events` returns the event history in chronological order.
- `POST /api/v1/cases/{case_id}/reports` verifies integrity, renders a PDF, stores it, and returns the report digest and download path.
- `GET /api/v1/cases/{case_id}/reports` lists stored reports.
- `GET /api/v1/cases/{case_id}/reports/{report_id}` downloads the PDF.

A missing case or report returns `404 Not Found`.

`GET /health` reports that the process is up. `GET /health/ready` also checks that SQLite accepts a query.

When `SCAMSHIELD_API_KEY` is set, send it on every `/api/v1` request:

```http
X-API-Key: your-local-key
```

Interactive documentation remains available without that header. The documented operations still require the key.

## Forensic evidence handling

SHA-256 maps input bytes to a fixed-size hexadecimal digest. For each new investigation, the service hashes the exact submitted text encoded as UTF-8. It does not normalize whitespace, punctuation, casing, newlines, or Unicode. A later integrity check hashes the currently stored content and compares that digest with the recorded baseline using a constant-time comparison.

The evidence collection timestamp is generated at submission using a timezone-aware UTC clock and stored in ISO 8601 form. Verification attempts also receive UTC timestamps and are recorded as evidence events. `VERIFIED` means the current stored text hashes to the recorded baseline. `FAILED` means the hashes differ. A `FAILED` result does not repair or overwrite the evidence. Cases created before forensic metadata existed have no fabricated timestamp or hash. Their integrity status is `UNAVAILABLE`.

The database migration adds nullable forensic columns to an existing `cases` table and creates `evidence_events` and `reports`. It does not recreate the cases table, rewrite existing content, or fabricate legacy metadata. It is safe to run repeatedly.

These hashes can help detect changes relative to the stored baseline, but storing both evidence and hash in the same SQLite database does not make that database tamper-proof: someone able to alter the database could change both. The hash alone does not prove when or by whom evidence was collected. This application does not claim a certified chain of custody or an independently verified collection time.

PDF reports repeat that limitation. Characters the report font cannot draw are shown as Unicode code points, and long lines may wrap for display. Neither change alters the stored evidence or its digest. The PDF's own SHA-256 is stored beside the investigation record. It is not printed inside the file, because embedding it would change the digest.

The bundled report fonts are DejaVu Sans and DejaVu Sans Mono. Their license is in `backend/app/assets/fonts/LICENSE`.

## Operational notes

This is a single-operator local application. SQLite is the system of record. Run one API process against a given database file. Put a reverse proxy with TLS in front of the containers before exposing them beyond your own machine, and set `SCAMSHIELD_API_KEY`. The application does not provide user accounts, and it does not delete evidence through the API.
